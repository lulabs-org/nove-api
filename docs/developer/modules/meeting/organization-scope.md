# 会议组织范围

`Meeting.orgId` 是会议数据的组织归属边界。会议列表、详情、参会人、创建、更新、删除和统计接口都使用统一认证上下文中的当前组织 ID，缺少组织上下文时拒绝请求；跨组织查询表现为记录不存在。

会议记录（Minute）继承所属会议的组织范围。会议记录列表和详情、转写、纪要总结、参会者总结以及按平台用户查询转写上下文，都会先验证所属会议属于当前组织；创建或重新关联会议记录时也不允许引用其他组织的会议。

腾讯会议和飞书的同步任务没有终端用户上下文。当前运行模式在 Webhook、WebSocket 或管理接口等入口使用启动时初始化的 `SingleOrgContextService`（管理接口优先使用认证上下文）解析一次组织；之后将 `orgId` 显式写入事件或队列负载，并贯穿 Handler、同步服务和第三方 API Client，底层会议服务不再读取全局默认组织。

当前运行模式仍要求数据库中恰好存在一个启用且未删除的组织。未来接入多组织时，只需在入口使用第三方集成标识解析 `orgId`，后续事件、队列和入库调用链保持不变。

## 部署与历史数据

迁移只增加可空的 `org_id`、外键和查询索引，不在 schema migration 中猜测历史数据归属。部署迁移后先执行只读预检：

```bash
pnpm db:backfill:meeting-org
```

确认输出的组织 ID 和待处理数量后再写入：

```bash
pnpm db:backfill:meeting-org -- --apply
```

当存在多个启用组织时必须显式指定目标组织：

```bash
pnpm db:backfill:meeting-org -- --org-id <organization-id> --apply
```

脚本会覆盖全部 `org_id IS NULL` 的会议（包括已软删除记录），完成后再次检查剩余数量必须为零。
